# Planted HQ: Projects, richer tasks, bulk chat tools

Build contract. Read with hq-design.md, hq-mcp.md, hq-phase-2.md section 11, brand-design-system.md and hq-simple-layouts.md. Owner brief (verbatim intent): turn the current task system into a calm, premium, relationship-focused project and task experience, and let ChatGPT/Claude create, organise and manage projects, milestones and tasks through MCP (including creating 30 to 50 tasks from a plan in one call). Extend what exists; do not rebuild HQ. Preserve every existing task, link and history row.

## 0. Why the chat stalled today

The MCP write cap is `DEFAULT_WRITE_HOURLY_LIMIT = 15` per person per hour (`lib/hq/mcp/limits.ts`, env `HQ_MCP_WRITE_HOURLY_LIMIT`), counted from `hq.ai_requests` rows prefixed `mcp write`. A launch plan of 30 tasks as 30 `create_task` calls therefore dies at call 16. Fix: (1) bulk tools that make ONE call and ONE transaction; (2) a separate, DB-enforced bulk budget so abuse protection stays; (3) raise the default single-write cap from 15 to 60 per hour (still env-overridable).

## 1. Data model (HQ schema, migrations 0142 onward; ACL in the last one)

Follow the conventions of the decisions/knowledge/meetings migrations (identity ref numbers, RLS forced, no direct API writes where an RPC is the path, audit, append-only histories, soft delete via `archive_record`, optimistic concurrency).

- **`hq.projects`**: `ref_number` ('PRJ-0001'), `name` (1..200, unique among live), `description` (<=5000), `owner_id` (active staff, default creator), `status` enum `hq.project_status` (planning, active, on_hold, completed, cancelled), `priority` (reuse `hq.task_priority`), `start_date`, `target_date` (>= start), `completed_at`, `notes` (<=50000 safe markdown; reuse the renderer in `lib/hq/knowledge`), created/updated stamps, soft delete (entity `project`).
- **`hq.project_milestones`**: `project_id`, `name` (1..200), `description`, `due_date`, `status` (open, done), `sort_order`, `completed_at`. Unique name per project.
- **`hq.project_links`**: exactly one of `contact_id`, `organisation_id`, `contractor_id`, `opportunity_id` per row; unique; (related contacts and organisations; also leads and contractors).
- **`hq.project_documents`**: `project_id`, `title`, `url` (https only, <=500), `added_by`. (Links to documents; no file storage in this phase: say so.)
- **Tasks extended (existing `hq.tasks`, keep all columns/rows/policies working):** add `project_id`, `milestone_id` (must belong to the same project), `parent_task_id` (subtasks, ONE level deep only, same project, never a cycle), `sort_order`, `blocked_reason` (optional text). `tasks.source` CHECK gains 'project' and 'bulk'. Existing task screens, search, lists, MCP tools, the Today and Reports sections and the decisions/meetings task links must keep working unchanged.
- **`hq.task_dependencies`**: `task_id`, `depends_on_task_id`; no self-dependency, no cycles (check in the RPC and a deferred constraint/trigger), both tasks visible to the caller, same project allowed or one without project allowed (cross-project allowed). A task is **blocked** while any dependency is not completed/cancelled.
- **`hq.task_checklist_items`**: `task_id`, `text` (<=300), `done`, `sort_order`, `done_by/at`.
- **`hq.task_comments`**: `task_id`, `author_id`, `body` (<=4000), `created_at`, `edited_at`; edit only by the author within a window or director.
- **`hq.task_activity`** and **`hq.project_activity`**: append-only (id, subject, actor_id or null for system, `at`, `kind` text, `summary` text, `detail jsonb`), written inside the RPCs and by a security-definer trigger on `hq.tasks` for direct updates (status, assignee, due date, priority, project, milestone, parent, completed). Readers see them only for tasks/projects they can see.
- **`hq.idempotency_keys`**: `staff_id`, `key` (8..80 chars), `scope` ('bulk_create_tasks' | 'bulk_update_tasks'), `request_hash`, `result jsonb`, `created_at`; unique (staff_id, scope, key); a replay with the same key and same request returns the stored result with `duplicate: true`; same key with a DIFFERENT request is refused (22023, plain message); keys expire after 48 hours (purge in the RPC opportunistically).
- **Views (security_invoker):** `project_overview` (counts of tasks by status, done/total, **progress %** (completed ÷ non-cancelled, subtasks not double counted: count top-level tasks only, with partial credit optional: keep it simple and documented), overdue count, blocked count, next milestone and its due date, **health**: `on_track` | `at_risk` | `off_track` | `done` | `on_hold` computed by documented rules: off_track if any overdue task has been overdue > 7 days or a milestone is overdue; at_risk if overdue tasks exist or the target date is within 14 days with progress < 60% ...; state the exact rules in the migration comment and test them), `task_overview` (task row + project ref/name + milestone name + parent title + subtask counts + checklist counts + blocked boolean + dependency counts + assignee name), `project_timeline` (milestones and dated tasks for the timeline view).
- **Function `hq.my_focus(p_limit int default 3)`** (security invoker or definer carefully): the caller's next actionable tasks ranked: not completed/cancelled, **not blocked**, not a parent that has open subtasks (the subtasks are the work), ordered by overdue first, then priority (urgent, high, normal, low), then due date (nulls last), then project priority, then oldest; returns task id, title, project, due, priority and a short `why` string (e.g. 'Overdue by 3 days', 'Urgent', 'Due today', 'Unblocks 2 tasks'). Also `hq.overdue_tasks(p_scope)`.
- **Capabilities:** reuse `tasks.read_all` / `tasks.write` for tasks; add `projects.read` (director, administrator, senior_property_manager, property_manager, business_development_manager, virtual_assistant, read_only) and `projects.write` (director, administrator, senior_property_manager, property_manager, business_development_manager, virtual_assistant); project visibility: everyone with `projects.read` sees projects; task visibility inside a project still follows the existing task rule (assignee, creator, tasks.read_all) so private tasks stay private; progress counts use only tasks the viewer can see (document this, and ALSO expose project-wide counts via the definer view only to people with `tasks.read_all`).

## 2. RPC contract (security definer, capability checked inside, MFA like other RPCs, pinned search_path, audit, revoke from public/anon, ACL registered)

`create_project(p_name, p_description, p_owner, p_status, p_priority, p_start, p_target, p_notes)`; `update_project(p_id, patch..., p_expected_version?)`; `set_project_status(p_id, p_status, p_note)`; `add_project_link/remove_project_link`; `add_project_document/remove`; `create_milestone(p_project, p_name, p_description, p_due)`, `update_milestone`, `complete_milestone` (refuses while it has open tasks unless `p_force` with a note), `reopen_milestone`, `reorder_milestones`; `create_project_task(...)` / extend existing task create/update RPC or table path with project, milestone, parent, sort_order; `complete_task(p_id, p_note)`; `add_task_dependency/remove_task_dependency`; `set_task_checklist(p_task, p_items jsonb)`; `add_task_comment/edit_task_comment`; **`bulk_create_tasks(p_tasks jsonb, p_idempotency_key text, p_project uuid default null, p_atomic boolean default false)`** and **`bulk_update_tasks(p_updates jsonb, p_idempotency_key text, p_atomic boolean default false)`**.

**Bulk semantics (the critical part):**
- 1..50 entries (refuse 0 and >50, plain message). Each entry: `ref` (caller-chosen local key, unique in the batch), `title` (required), `description`, `assignee` (staff id, default the caller), `priority`, `status`, `due_date`, `project` (id; default the batch `p_project`), `milestone` (id OR milestone name within the project), `parent_ref` (subtask of another entry in the batch or an existing task id), `depends_on` (list of batch refs or existing task ids), `checklist` (list of strings), `linked_contact/organisation/contractor` ids.
- Validation per entry with the same rules as single creation, plus: dependency cycles inside the batch are detected, a `depends_on` ref must exist in the batch or be a visible existing task, milestones must belong to the project, assignees must be active staff, only people with `tasks.write` (and `projects.write` when a project is set) may call; assigning to someone else follows the existing task-assignment rule.
- Execution in ONE transaction. `p_atomic = true`: any invalid entry fails the whole batch (nothing written). `p_atomic = false` (default): valid entries are created (each in a savepoint), invalid ones are returned in `failed` with `index`, `ref`, and `errors[]` in plain language; entries that depend on a failed entry fail with a clear message ("depends on <ref>, which failed").
- Returns `{created: [{index, ref, id}], failed: [{index, ref, errors[]}], duplicate: boolean, created_count, failed_count}`; replays by idempotency key return the original result with `duplicate: true` and create nothing.
- **Rate limits (DB-enforced, abuse protection kept):** a per-person budget function `hq.consume_bulk_budget(p_calls int, p_items int)` enforcing at most **6 bulk calls and 300 bulk items per rolling hour** (settings `bulk_calls_per_hour` default 6 and `bulk_items_per_hour` default 300, director-adjustable within 1..60 and 1..2000), raising a clear error with SQLSTATE 54000 and hint `bulk_rate_limited`; the call also counts as ONE request against `ai_hourly_limit`. Audit: one audit event for the batch (counts, project, key hash) plus the normal per-row audit/activity writes, and each task gets `source = 'bulk'` and an activity row 'Created in bulk'.
- `bulk_update_tasks`: entries `{id, status?, assignee?, priority?, due_date?, project?, milestone?, title?, description?, add_dependency?, complete?}`; same per-entry validation, savepoints, atomic flag, idempotency, bulk budget (items counted), visibility and permission rules identical to single updates (you cannot update a task you cannot update singly).

### 6.4 Focus functions (security definer, any active staff)

- `hq.my_focus(p_limit integer default 3)` returns table `(task_id uuid, title text, status task_status, priority task_priority, due_date date, project_id uuid, project_ref text, project_name text, milestone_name text, overdue_days int, unblocks int, why text, rank int)`. Tasks assigned to the caller, open, not blocked, not a parent with open subtasks. - `hq.overdue_tasks(p_scope text default 'mine', p_project uuid default null)` returns table `(task_id, title, status, priority, due_date, overdue_days int, assigned_to, assignee_name, project_id, project_ref, project_name, is_blocked bool)`. `mine` = assigned to the caller; `all` = every task the caller can see (task rule); other scopes 22023 "scope is mine or all"; `p_project` needs `projects.read`. At most 200, oldest due first.

### 6.5 RPCs (exact signatures; all return jsonb unless stated)

Projects (`projects.write`). Project json = `{project_id, ref, ref_number, name, status, priority, owner_id, start_date, target_date, completed_at, version, updated_at}`.
- `create_project(p_name text, p_description text = null, p_owner uuid = null, p_status project_status = 'planning', p_priority task_priority = 'normal', p_start date = null, p_target date = null, p_notes text = null)` -> project json + `{changed}`. Owner default caller (22023 "the project owner must be an active member of staff"); 23505 hint `project_name_taken` `a project called "X" already exists` (case/space-insensitive among live); 22023 "the target date cannot be before the start date".
- `update_project(p_id uuid, p_expected_version integer = null, p_name text = null, p_description text = null, p_owner uuid = null, p_status project_status = null, p_priority task_priority = null, p_start date = null, p_target date = null, p_notes text = null, p_clear text[] = null, p_note text = null)` -> project json + `{changed, changed_fields[]}`. Null leaves a field; `p_clear` in `description, owner, start_date, target_date, notes`; stale version 23514 hint `project_stale`; version + 1 per change; `p_note` (<=300) goes into the audit row and activity.
- `set_project_status(p_id uuid, p_status project_status, p_note text = null)` -> same as update_project.
- `add_project_link(p_project uuid, p_kind text, p_id uuid)` -> `{project_id, link_id, kind, record_id, label, changed}`; kinds `contact | organisation | contractor | opportunity`; the record must be live and readable (growth.read / contractors.read) else P0002 "linked <kind> not found". `remove_project_link(p_project uuid, p_kind text, p_id uuid)` -> `{project_id, kind, record_id, changed}`.
- `add_project_document(p_project uuid, p_title text, p_url text)` -> `{project_id, document_id, title, url, changed}` (22023 "a document link is an https:// address of at most 500 characters"; 23514 hint `project_document_limit` past 50). `remove_project_document(p_project uuid, p_document bigint)` -> `{project_id, document_id, changed}`.
- Milestone json = `{milestone_id, project_id, name, description, due_date, status, sort_order, completed_at}`. `create_milestone(p_project uuid, p_name text, p_description text = null, p_due date = null, p_sort_order integer = null)` (23505 hint `milestone_name_taken`; max 100); `update_milestone(p_id uuid, p_name text = null, p_description text = null, p_due date = null, p_clear text[] = null)` (clear `description`, `due_date`); `complete_milestone(p_id uuid, p_force boolean = false, p_note text = null)` -> + `{changed, open_tasks}` (open tasks: 23514 hint `milestone_open_tasks`; force without note 22023 hint `milestone_force_note`; counts ALL open tasks of the milestone, not only visible ones); `reopen_milestone(p_id uuid)`; `reorder_milestones(p_project uuid, p_ids uuid[])` -> `{project_id, order, changed}` (must list every milestone once).
- `archive_record('project', id, reason)` / `restore_record('project', id)`: `projects.write`; tasks are left as they are; restore refused 23505 when a live project took the name.

Tasks. Task json = `{task_id, title, status, priority, due_date, assigned_to, project_id, milestone_id, parent_task_id, sort_order, source, updated_at}`. "Can update" = `tasks.write` and live and (assignee or creator or `tasks.read_all`); otherwise P0002 "task not found".
- `create_project_task(p_title text, p_project uuid = null, p_milestone uuid = null, p_parent uuid = null, p_assignee uuid = null, p_due_date date = null, p_priority task_priority = 'normal', p_description text = null, p_status task_status = 'to_do', p_depends_on uuid[] = null, p_checklist text[] = null, p_sort_order integer = null, p_blocked_reason text = null)` -> task json + `{changed}`. `tasks.write` (+ `projects.write` in a project). Source `project` in a project, else `manual`. Project defaults to the parent's. Same rules as a bulk entry.
- `update_project_task(p_id uuid, p_patch jsonb)` -> task json + `{changed, changed_fields[]}`. Patch = a bulk-update entry without `id`.
- `complete_task(p_id uuid, p_note text = null)` -> task json + `{changed}` (note <= 300 as a `note` activity row; completing a blocked task is allowed).
- `add_task_dependency(p_task uuid, p_depends_on uuid)` / `remove_task_dependency(p_task uuid, p_depends_on uuid)` -> `{task_id, depends_on_task_id, changed, blocked}`. 22023 "a task cannot depend on itself"; 23514 hint `task_dependency_cycle` `that would make a cycle: "<title>" already waits for this task`; P0002 "the task it depends on was not found" (not visible); max 50 (hint `task_dependency_limit`). Cross-project allowed.
- `set_task_checklist(p_task uuid, p_items jsonb)` -> `{task_id, total, done, changed, items: [{id, text, done, sort_order}]}`. Items: `"text"` or `{text, done?, id?}`; an item with an existing id keeps its done stamp; unlisted items are removed; max 50 (hint `task_checklist_limit`).
- `add_task_comment(p_task uuid, p_body text)` -> `{comment_id, task_id, body, created_at, changed}` (`tasks.write`, task visible). `edit_task_comment(p_comment bigint, p_body text)` -> `{comment_id, task_id, body, edited_at, changed}`: author within 60 minutes (with `tasks.write`) or `settings.admin`; else 42501 hint `task_comment_edit_window`.

Bulk.
- `bulk_create_tasks(p_tasks jsonb, p_idempotency_key text, p_project uuid = null, p_atomic boolean = false)` -> `{created: [{index, ref, id, title}], failed: [{index, ref, errors: [text]}], duplicate: bool, created_count, failed_count, atomic, rolled_back, project_id}` (`index` is 0-based; `ref` null when not given). Entry fields (any other key: `unknown field "x"`): `ref` (1..80, unique in the batch), `title` (required, <=200), `description` (<=4000), `assignee` (staff uuid, default caller, active staff), `priority`, `status`, `due_date` (YYYY-MM-DD, within five years), `project` (uuid; default `p_project`, then the parent's project), `milestone` (uuid or name in the project, case/space-insensitive), `parent_ref` or `parent` (a batch ref or an existing visible task id), `depends_on` (string or list of batch refs / existing visible task ids, max 50), `checklist` (list of text or `{text, done}`, max 50), `linked_contact`, `linked_organisation`, `linked_contractor`, `linked_opportunity` (uuids, readable), `sort_order` (0..100000; default next in the project), `blocked_reason` (<=500). Typical error texts: "a task needs a title", "priority is low, normal, high or urgent", "status is to_do, in_progress, waiting, completed or cancelled", "due_date must be a date (YYYY-MM-DD)", "a due date must be within the next five years", "the person a task is assigned to must be an active member of staff", `there is no milestone "X" in this project`, "a milestone needs a project", `depends_on "x" is not a task in this batch or an existing task id`, "the task it depends on was not found", "parent task not found", the subtask rules above, `ref "x" is used by more than one entry`, cascades "depends on <ref>, which failed" and "its parent <ref> failed" (`<ref>` = the ref, or `#n` 1-based when none), and "<ref> is part of a dependency cycle inside this batch". Caller needs `tasks.write`, and `projects.write` when `p_project` or ANY entry names a project (42501 for the whole call).
- `bulk_update_tasks(p_updates jsonb, p_idempotency_key text, p_atomic boolean = false)` -> `{updated: [{index, id, changed: [field]}], failed: [{index, id, errors: [text]}], duplicate, updated_count, failed_count, atomic, rolled_back}`. Entry fields: `id` (required), `title, description, assignee, priority, status, due_date, project, milestone, parent, add_dependency (id or list), remove_dependency (id or list), complete (true), checklist (as set_task_checklist), comment (<=4000, adds a comment), sort_order, blocked_reason`. Only present fields change; JSON null clears `assignee, due_date, project, milestone, parent, description, blocked_reason`. `changed` names: `title, description, priority, status, due_date, assignee, project, milestone, parent, sort_order, blocked_reason, add_dependency, remove_dependency, checklist, comment`. Rules = single update: P0002 "task not found" when the caller cannot update it; reassigning to someone else needs creator or `tasks.read_all` (42501 hint `task_assign_rule` "only the person who created this task, or someone who can see everyone's tasks, can give it to someone else"); changing project or milestone needs `projects.write`.
- Shared bulk rules: 1..50 entries (22023 hint `bulk_size`: "give at least one entry in tasks|updates", "at most 50 entries in one call (N given): split the plan into calls of 50 or fewer", "tasks must be a list", "each task must be an object"); key 8..80 characters (22023 hint `idempotency_key_shape`); one transaction, a savepoint per entry; atomic failure = nothing written, `rolled_back: true`, `created`/`updated` empty, `failed` lists the failing entries only; idempotency per (caller, scope, key) for 48 hours (expired keys purged when that person next calls), request hash = sha-256 of the canonical JSON of (tasks/updates, project, atomic); replay returns the stored result with `duplicate: true`, writes nothing, uses no budget, writes no audit event; same key + different request: 22023 hint `idempotency_key_reused` "that idempotency key was already used for a different request: use a new key for a new plan". Budget check happens after the replay check and before any entry; a refused call (size, permission, budget) writes nothing; an atomic call that rolled back still used its budget and is still audited. One `audit_events` row per call: `action` `bulk_create` | `bulk_update`, `entity_type` `task_batch`, `entity_id` = `p_project` (or null), `changes` = `{entries, created|updated, failed, atomic, rolled_back, project_id, key_hash}`; plus the normal per-row task audit. One `project_activity` row `bulk_created` per project per call (`detail {count, task_ids}`), no per-task project rows. The ONE `hq.ai_requests` row per MCP call is written by the MCP server (`lib/hq/mcp`), not by these RPCs.
- `consume_bulk_budget(p_calls integer, p_items integer)` -> `bulk_budget()` after the use. Exact limits: at most `bulk_calls_per_hour` (default **6**) calls and `bulk_items_per_hour` (default **300**) items per person per rolling hour (`bulk_usage.at > now() - 1 hour`); a call that would exceed either raises 54000 hint `bulk_rate_limited` ("bulk limit reached: at most 6 bulk calls per hour; try again later" / "bulk limit reached: at most 300 tasks per hour through bulk calls (N used); try again later or send fewer"; `detail` "N of M calls|items used in the last hour") and uses nothing. So the 6th call in an hour passes and the 7th is refused; 300 items pass and the 301st is refused. Each bulk call consumes 1 call and N items (N = entries, valid or not). 22023 for p_calls outside 0..60, p_items outside 0..2000, or both 0.
- `bulk_budget()` -> `{calls_per_hour, items_per_hour, calls_used, items_used, calls_remaining, items_remaining}`.

### 6.6 Deviations and notes

- No definer view for project-wide counts (see 6.3); `tasks.read_all` holders get project-wide figures from `project_overview`.
- One extra table not named in section 1: `bulk_usage` (the rolling-hour budget ledger); plus extra RPCs `update_project_task`, `bulk_budget` (read the budget) and the `comment` / `remove_dependency` / `checklist` / `parent` / `sort_order` / `blocked_reason` fields on bulk updates.
- Comment edit window: 60 minutes (author), any time for directors (`settings.admin`).
- `complete_task` does not refuse a blocked task or a parent with open subtasks (the UI may warn).
- Tests: `hq_17a_projects.sql` (193) and `hq_17b_bulk.sql` (122). Existing exact totals updated in `hq_01` (45 tables, 104 hq functions, 100 for authenticated, 103 definer, 20 views, task columns, 134 capability rows) and `hq_02` (capability lists, 28 director capabilities, 134 rows, the new tables in the zero-rows check).
